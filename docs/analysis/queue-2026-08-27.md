# Work queue, 2026-08-27

Recorded from the maintainer, in their priority order. **Nothing here has been
started.** Two premises are questioned at the end; read those before costing
items 3 and 4.

## 1. APK download and update path — harden it as a state machine

Roblox ships a client roughly weekly and rejects old ones server-side quickly,
so this is a recurring blocking event rather than a rare one. Fetch-on-first-launch
is correct and stays.

    download to temp        never overwrite the current install in place
    verify signature + ABI  before anything else; reject on mismatch
    stage alongside current using the existing per-instance data root layout
    launch the staged one
    promote on LAUNCH success only -- a running state, login screen rendered or
                            first frame -- and demote the previous to N-1
    revert automatically    on launch failure, or a crash within N seconds
    blocklist the hash      of a failed version; never auto-retry it

The blocklist is not optional. Without it: broken version fails, rollback
succeeds, next launch sees a version mismatch, re-downloads the same broken
APK, and the loop closes.

**The distinction that makes this worth building: "last known good" must mean
last successfully *launched*, not last successfully *downloaded*.** An APK can
download cleanly, verify cleanly, and still fail at load, and promoting at
download time overwrites the only working copy with it.

mocktail already does download-on-first-launch, keeps the last working copy,
and checks signature and ABI before loading native code. It does not clearly
separate download-success from launch-success. That separation is the part to
do better.

## 2. Voice chat — finish it, before rearchitecting anything

Output works, so the input path mirrors plumbing that already exists. Needed: an
`AudioRecord` JNI implementation, a mic capture path (AAudio or OpenSL ES
input), and a `RECORD_AUDIO` permission stub the client accepts. Then verify
WebRTC's capture path actually binds to it end to end.

Deliberately first, and deliberately before any rearchitecting: it is the
feature most likely to trip server-side checks, so whether it works at all is
worth knowing before anything is built around it.

## 3. Replace the mocktail web view dependency

Not a licensing matter, and nobody should spend time treating it as one.
mocktail is Apache-2.0: the source may be read, ported from and modified. The
obligations are attribution, retaining `NOTICE`, and stating that changes were
made. A clean-room process defends against copying code you have no licence
to, which is not the situation.

The reason is architectural: a third-party runtime should not be a hard
dependency inside our own runtime. Replacement to be a standalone Rust crate on
gtk4-rs and the webkit6 bindings, with a small, documented FFI surface.

## 4. Rust migration — scoped, not wholesale

**Do not rewrite the C core.** A bionic-to-glibc shim, an AOSP loader and a JNI
VM are ABI-boundary work; in Rust they become almost entirely `unsafe extern
"C"` with raw pointers and hand-laid struct layout. Months of effort against
working code for close to no memory-safety benefit.

Where Rust pays, incrementally: the web view and UI shell (item 3, the
beachhead), APK fetch and signature verification, the update state machine from
item 1, config parsing.

Sequencing: voice chat first, since it is independent. Then build the update
state machine in the new Rust crate rather than writing it in C and porting it
later -- item 1 and item 4's first target are the same code.

## Two premises to check before costing items 3 and 4

**Cordial's web view may already be what item 3 describes.**
`crates/cordial-shell/src/webview.rs` is an in-process `WebKitWebView` in Rust
via gtk4-rs, chosen under ADR-011 because the engine's surface is a subsurface
of an `AdwWindow` and a second Wayland connection is not available. Whether
anything still links `third_party/mocktail-webview/` is an open question and
decides whether item 3 is a rewrite, a deletion, or already done.

**Item 4's other targets appear to be Rust already.** `cordial-update` does APK
fetch and signature verification; the update machinery and config parsing are
in `cordial-update`/`cordial-shell`. If so, item 4's incremental targets are
complete and the item reduces to item 1's new state machine.

Both stated as questions rather than corrections, because they were established
in a one-day audit and not by the person who wrote the queue.

## Observation to design from, not around

On a phone: connecting a keyboard and mouse and using them switches Roblox to
desktop controls; touching the screen switches back instantly. **The engine
follows the last-used device, per event, reversibly.**

This matters because the touch work was heading toward a static `isTouchDevice`
decision plus a user-facing setting, on the strength of Sober #1577 reporting an
irreversible flip on a hybrid laptop. If the real client switches per event,
that design is wrong: Cordial should report every capability it has and let the
engine follow the input, and #1577 is then a symptom of something not being
reported rather than a policy question.
